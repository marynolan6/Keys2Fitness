# Mobile UI design: a learning guide for Keys2Fitness

**Research checked November 25, 2026.** Start with the [app critique and screenshots](mobile-ui-design-review.md). The [theme standards](theme-standards.md) describe approved decisions. This guide explains how to evaluate the next decision. A course example or a competitor's feature does not override a product requirement.

## Where to start

If the team has one afternoon, read [NN/g on visual hierarchy](https://www.nngroup.com/articles/principles-visual-design/), work through [Material 3's color-role example](https://developer.android.com/codelabs/jetpack-compose-theming), and read [Figma's lesson on documenting a system](https://help.figma.com/hc/en-us/articles/14552804059927-Lesson-4-Document-and-manage-your-system). Then give two teammates the same coach inbox brief. Compare what they draw separately. The differences will identify which decisions the team's guide still leaves to taste.

## Courses, workshops, and practical lessons

The notes below come from public lessons, transcripts, codelabs, or syllabi. **Syllabus** means the outline was reviewed, not that the paid training was taken. The exercises are proposed K2F practice. Use a sketch, paper prototype, or separate design file. No app changes are needed to learn from them.

| Resource and format | What to study | Apply it to K2F |

| [CalArts: Visual Elements of User Interface Design](https://www.coursera.org/learn/visual-elements-user-interface-design) · Coursera syllabus | Formal, active, and compositional elements. Modules 3 and 4 connect control states to hierarchy, grids, and a UI inventory. | Print Coach Home in grayscale. Mark what draws the eye first, then what the coach should do first. Are they the same thing? |

| [Figma: Introduction to design systems](https://help.figma.com/hc/en-us/articles/14552901442839-Overview-Introduction-to-design-systems) · four written lessons, videos, practice file | When a system is useful; defining, building, and maintaining it. | [Android Basics with Compose: Display lists and use Material Design](https://developer.android.com/courses/android-basics-compose/unit-3) · course unit | The scrollable-list and “Build beautiful apps” pathways join list structure, styling, and accessibility. | Draw five workout templates as comparable rows. | [Google: Theming in Compose with Material 3](https://developer.android.com/codelabs/jetpack-compose-theming) · public codelab | The Reply example pairs foreground and container colors, defines complete type styles, and varies emphasis without reducing legibility. | Create a swatch for the **pair** `action label on action fill`. ## Platform and visual references

| Question | References | Decision they inform |
| --- | --- | --- |
| What makes a screen feel clean? | [NN/g: Five principles of visual design](https://www.nngroup.com/articles/principles-visual-design/) · [Apple: UI Design Dos and Don'ts](https://developer.apple.com/design/tips/) | Rank content with scale, alignment, proximity, and contrast. Give the next action more emphasis than the label of the screen. |
| Card or row? | [NN/g: Cards](https://www.nngroup.com/articles/cards-component/) · [Android: Layout basics](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-basics) | Use a card for a coherent object with a distinct action, such as today's workout. For comparing many similar objects, try a list with predictable positions first. |
| Where should expression live? | [Google Design: Material 3 Expressive research](https://design.google/library/expressive-material-design-google-research) · [Apple HIG: Materials](https://developer.apple.com/design/human-interface-guidelines/materials) | Google's research tests what stands out and how quickly people act. Apple's materials distinguish controls from content. Both support purposeful emphasis. Neither proves a particular K2F style will win. |
| Is a plus a destination? | [Android: Floating action button](https://developer.android.com/develop/ui/compose/components/fab) · [Apple HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars) | A FAB conventionally promotes a focused action; tabs identify destinations. A custom menu can work, but test whether a new client predicts what it opens. |
| Which action should be loudest? | [Apple HIG: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) · [USWDS: Buttons](https://designsystem.digital.gov/components/button/) | Distinguish the likely action, explicit selection, dismissal, and destruction. Treat the approved red menu Close as a documented exception, not a recipe for every modal. |
| How should type and copy sound? | [Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography) · [IBM Carbon: Typography](https://www.carbondesignsystem.com/building-blocks/foundations/typography/overview) · [Apple HIG: Writing](https://developer.apple.com/design/human-interface-guidelines/writing) | Keep expressive welcome text separate from dense working text. Use factual coaching language: “No videos waiting” describes the data; “On track” makes a broader claim. |
| How should navigation adapt? | [Android: Canonical layouts](https://developer.android.com/develop/ui/compose/layouts/adaptive/canonical-layouts) · [Android: System bars](https://developer.android.com/design/ui/mobile/guides/foundations/system-bars) | On a tablet, use extra space when showing an item beside a list helps. Keep the status-bar icons readable against the actual content behind them. |
| When is motion appropriate? | [Apple HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion) · [Apple HIG: Launching](https://developer.apple.com/design/human-interface-guidelines/launching) · [RN 0.88: AccessibilityInfo](https://reactnative.dev/docs/0.88/accessibilityinfo) | Prefer motion that explains a change. For decorative motion, design the reduced-motion and returning-user experiences at the same time. |

## Accessibility and data presentation

- [Android touch targets](https://support.google.com/accessibility/android/answer/7101858?hl=en), [Apple touch guidance](https://developer.apple.com/design/tips/), and [WCAG 2.2 target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) use **different units and scopes**: Android recommends 48 × 48 dp with spacing; Apple recommends 44 × 44 pt; the web AA criterion is 24 × 24 CSS px with exceptions. Keep K2F's 48-unit mobile target. Check the visible arrow *separately* from the tappable rectangle.
- [WCAG text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html), and [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/) explain the 4.5:1 normal-text and 3:1 large-text/meaningful-control benchmarks, exceptions for inactive controls, and how to apply WCAG principles to non-web software. WCAG2ICT is informative guidance. Passing one comparison is not native app certification.
- [WAI: Labeling controls](https://www.w3.org/WAI/tutorials/forms/labels/), [GOV.UK: Error messages](https://design-system.service.gov.uk/components/error-message/), and [RN 0.88: Accessibility](https://reactnative.dev/docs/0.88/accessibility) connect visible labels, field-specific recovery, names, roles, and states. A rep target in a box is a hint; “Actual reps” remains visible after typing. In the meal editor, say which field needs attention.
- [Apple HIG: Charts](https://developer.apple.com/design/human-interface-guidelines/charts) and [WAI: Complex images](https://www.w3.org/WAI/tutorials/images/complex/) distinguish the takeaway from the detailed values. Keep pounds, date range, actual time spacing, and a text route to the readings. A downward line alone doesn't say whether someone's fitness goal is being met.

## Team practice and real products

- [Figma: Create and use variants](https://help.figma.com/hc/en-us/articles/360056440594-Create-and-use-variants) and [component and library best practices](https://www.figma.com/best-practices/components-styles-and-shared-libraries/) show how named properties, stable instances, and descriptions reduce handoff guesswork. Model meaningful states; don't generate every theoretical combination. Use one team file if publishing a shared library is unavailable.
- [Figma: Tokens, variables, and styles](https://help.figma.com/hc/en-us/articles/18490793776023-Update-1-Tokens-variables-and-styles) and the [DTCG format specification](https://www.designtokens.org/tr/2025.10/format/) explain aliases and portable token data. A name such as `action.primary.foreground` lets teams share intent. The DTCG document is a Community Group report, not a W3C Recommendation; it doesn't require K2F to migrate `theme.ts` or buy tooling.
- [GOV.UK contribution criteria](https://design-system.service.gov.uk/community/contribution-criteria/) and the [USWDS maturity model](https://designsystem.digital.gov/maturity-model/) give a small team a workable rule: show the repeated need, demonstrate that reuse won't solve it, test in context, and give the decision an owner. Adopt through one real flow first.
- [NN/g: Testing visual design](https://www.nngroup.com/articles/testing-visual-design/) and [Usability testing 101](https://www.nngroup.com/articles/usability-testing-101/) answer different questions. Ask what the app *feels* like in a first-impression exercise; observe whether someone can do the work in a separate task. A preference vote can't establish task success.
- **Fitness comparators, not standards:** [Strong's workout walkthrough](https://help.strongapp.io/article/229-my-first-workout) places per-set entry and a checkbox together; [Hevy's previous-workout values](https://www.hevyapp.com/features/track-exercises/) explicitly labels the source of suggested numbers. Strong's walkthrough is historical and both sources are vendor descriptions. In K2F the hints come from a **coach prescription**, not a past performance. Keep that distinction, the user's custom zero, and the separate read-only summary.

## Worked handoff for two contributors

Suppose one contributor designs a workout action and another implements it. “Make a blue button” allows both the 2.84:1 and 5.66:1 combinations in the [audit](mobile-ui-design-review.md). An example of a useful **proposed** handoff:

| Decision | What to give the next person |
| --- | --- |
| Intent and scope | `Action / Primary`: one likely next action in a task region, such as **Continue workout**. Show a counterexample: **All (3)** means selected filter, not submit. |
| Design-to-code mapping | Figma variant `intent=primary, state=default`; existing RN example [AssignedWorkoutCard](../src/components/AssignedWorkoutCard.tsx); background `colors.primaryDark` and foreground `colors.surface` in [theme.ts](../src/theme.ts). These variant names are a proposal, not an existing Figma file. |
| States | Show default, pressed, keyboard-focused, disabled, and saving if the action writes. Say what gets announced, what prevents a second submission, and where focus goes. Show the action in context once with long copy. |
| Layout | Specify the leading edge, adjacent items, gap token, minimum target, and wrap/stack behavior. Name the type role with size, weight, and line height. Include both a normal phone and 320 dp at 1.5× text. Don't solve overflow by shrinking labels. |
| Ownership and evidence | Record the decision, date, owner, screenshot/fixture, contrast pair, and which old example it supersedes. Note physical-device and screen-reader checks as **observed** or **untested**. Ask a second contributor to recreate it without a verbal walkthrough. |

**For an agent starting a UI task:** Read the relevant current standard, inspect the most recent shipped screen, find the component that already owns the behavior, and identify what the user explicitly wants preserved. Cite one relevant source for a disputed tradeoff. Distinguish “measured,” “observed,” and “proposed.” Seek a product decision if research conflicts with an approved interaction. This guide gives future sessions a shared reference; it doesn't change model training or turn the proposals into policy.
